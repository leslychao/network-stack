# Network stack

Личный VPN и Telegram-прокси на Ubuntu 24.04 или 26.04 LTS. Настройка из одного GitHub Actions Secret, установка Docker по SSH, автоматическое создание первого VLESS-доступа и обновления с откатом базы панели.

Домен не нужен: панель доступна по `https://<PANEL_HOST>:9443`, где `PANEL_HOST` — публичный IPv4 VPS. Caddy получает доверенный IP-сертификат Let's Encrypt с профилем `shortlived` и автоматически продлевает его. Порт `80` должен оставаться доступным для HTTP-проверки; TLS-ALPN на занятом VPN порту `443` отключён. Email для ACME не требуется. [IP-сертификаты Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability/).

| Сервис | Образ | Внешний TCP-порт |
|---|---|---|
| VPN и панель | `ghcr.io/mhsanaei/3x-ui:v3.8.0` | VPN `443`; HTTP панели только `127.0.0.1:2053` |
| Telegram | `nineseconds/mtg:2.2.8` | `8443` |
| HTTPS панели | `caddy:2.11.4-alpine` | `9443`, HTTP/ACME `80` |

Точные digest закреплены в `compose.yaml`. JSON/TOML/Caddyfile и обычные значения по умолчанию находятся там же. Собственных Docker-образов и зависимости от Python-пакетов нет: скриптам нужен Python 3.10+ и Docker Compose 2.23.1+.

При подготовке релиза скрипт создаёт `.runtime/mtg.toml` из `x-mtg-config`: на Linux файл имеет права `0600` и принадлежит UID mtg. Каталог — `0700`, внутри контейнера файл подключается только для чтения. Это обходит ограничение Compose: у inline-конфигов права и владелец игнорируются.

## Подготовка VPS

1. Создайте отдельный VPS с Ubuntu 24.04 или 26.04 LTS, публичным IPv4 и минимум 1 ГБ RAM. Для проверок используется amd64; образы также публикуются для arm64.
2. Создайте отдельный SSH-ключ без passphrase для Actions и установите публичную часть на сервер. Пользователь должен быть root либо иметь `sudo -n` без пароля. SSH работает на порту `22`.
3. Укажите публичный IPv4 в `PANEL_HOST`. Покупка домена и настройка DNS-записи не нужны.
4. Разрешите входящие TCP `22`, `80`, `443`, `8443`, `9443` в firewall провайдера. Убедитесь, что порты свободны. Docker публикует порты через свои правила; обычные правила UFW для входящего трафика могут их не ограничивать.
5. Проверьте отпечаток SSH host key через доверенную консоль провайдера. Сохраните соответствующую запись в отдельный `known_hosts`. `ssh-keyscan` сам по себе не подтверждает подлинность ключа.

Скрипт установки использует официальный APT-репозиторий Docker. Уже установленный подходящий Docker не обновляется. Конфликтующие runtime-пакеты автоматически не удаляются. На сервере нужны исходящие HTTPS, DNS, NTP и доступ к Telegram DC; часы должны быть синхронизированы.

## Единственный секрет DEPLOY_ENV

Скопируйте `.env.example` в `.env` и заполните все поля либо создайте файл автоматически. Команда ниже выполняется на доверенном компьютере с работающим Docker; параметры не содержат паролей:

```bash
python3 scripts/generate_env.py \
  --ssh-host 203.0.113.10 \
  --ssh-user root \
  --ssh-key /path/to/deploy_ed25519 \
  --known-hosts /path/to/verified_known_hosts \
  --mtg-domain www.microsoft.com
```

На Windows используйте `py` вместо `python3` и абсолютные Windows-пути. Команду можно записать одной строкой. Генератор не перезаписывает существующий `.env` и не печатает ключи или пароль. Для `--mtg-domain` выберите доступный TLS-сайт, подходящий для маскировки; это имя включается в секрет Telegram. Для REALITY исходный target — `www.microsoft.com:443`, он задаётся в `x-bootstrap`.

По умолчанию `PANEL_HOST` совпадает с `SSH_HOST`; при необходимости его можно указать через `--panel-host`. Имя сайта для маскировки MTProto/REALITY не является доменом панели и не требует владения этим сайтом.

В **Settings → Secrets and variables → Actions** создайте **один repository secret `DEPLOY_ENV`** и вставьте всё содержимое `.env`. При установленном GitHub CLI:

```bash
gh secret set DEPLOY_ENV < .env
```

В PowerShell:

```powershell
Get-Content -Raw .env | gh secret set DEPLOY_ENV
```

Формат: `KEY=value` или `KEY='literal value'`, пустые строки и комментарии с `#`. В одинарных кавычках `$`, `#`, пробелы и shell-конструкции остаются данными; `\'` обозначает апостроф, `\\` — обратную косую черту. Двойные кавычки и многострочные значения не поддерживаются. SSH-ключ и `known_hosts` передаются одной строкой Base64. Пароль панели — 16–72 UTF-8 байта. Настройки сторонних путей, `COMPOSE_*` и неизвестные ключи запрещены.

`.env` содержит реальные секреты. Храните его в защищённом месте; на Windows ограничьте доступ ACL. SSH-ключ не копируется на VPS и не передаётся контейнерам. GitHub получает только один пользовательский секрет; встроенный `GITHUB_TOKEN` нужен лишь для checkout.

## Первый деплой

Push в `main` запускает проверки, затем выкладку. Доступен и **Actions → Network stack → Run workflow**, также из `main`. PR запускают только проверки без секретов.

Actions устанавливает необходимые компоненты на VPS, передаёт релиз по SSH и запускает серверную операцию под systemd. Обрыв SSH не прерывает уже запущенную выкладку. Одновременные операции исключены блокировкой сервера; общий предел операции — 15 минут плюс время на откат.

До открытия HTTPS-панели CLI 3x-ui задаёт администратора, затем API с cookie и CSRF создаёт VLESS + REALITY + Vision и одного пользователя. Прерванная настройка продолжается без дублирования inbound. После проверки записывается маркер завершения.

Откройте `https://<PANEL_HOST>:9443/`. Начальные имя и пароль находятся в `.env`. Далее смените пароль и при необходимости включите 2FA в панели. QR-код и `vless://` доступны в разделе клиентов; адрес подключения VPN — IP VPS на порту `443`, SNI REALITY — выбранный masking target.

Для Telegram локально сформируйте ссылку `tg://proxy?server=IP_ИЛИ_ДОМЕН&port=8443&secret=ЗНАЧЕНИЕ_MTG_SECRET` и откройте её на устройстве. Ссылка содержит доступ к прокси: её не следует размещать в Git, Actions logs или публичных artifacts.

### Кто управляет настройками

- `compose.yaml` управляет образами, опубликованными портами, ресурсами, Caddy и конфигурацией mtg. Панель слушает HTTP на `2053` с базовым путём `/`; изменение этих инфраструктурных настроек требует согласованной правки Compose и bootstrap.
- `INITIAL_*` используются только при первой настройке. После её завершения их изменение в GitHub Secret не меняет пароль, 2FA, пользователей и REALITY-ключи. Удалённый в панели доступ не создаётся снова. Для ротации используйте панель.
- SQLite 3x-ui — источник актуальных VPN-доступов. `MTG_SECRET` остаётся источником доступа Telegram; его изменение применяется при деплое. Сертификатами и TLS-ключами управляет Caddy.
- Панель и встроенный Xray обновляйте закреплённым образом через Actions. Обновление ядра из UI меняет файловую систему контейнера и теряется при пересоздании.

## Обновление и откат

Перед изменением работающих сервисов выполняются проверки образов, Caddy и диагностика mtg. `mtg doctor` в закреплённой версии возвращает код 1 также при несовпадении IP стороннего masking-домена с IP прокси и при небольшом дрейфе часов. Эти два результата выводятся как рекомендации. Недоступность Telegram DC, masking-сайта, DNS/NTP, чрезмерный дрейф, неправильная конфигурация и неизвестный формат диагностики блокируют деплой. Допуски времени и IP в конфигурации не подменяются.

Затем публичная панель закрывается, 3x-ui останавливается и создаётся согласованный снимок SQLite вместе с маркером первоначальной настройки. После запуска проверяются панель, процесс и конфигурация Xray, mtg и HTTPS с проверкой цепочки сертификата и IP-адреса. Пароль администратора и сохранность первого клиента для этих проверок не нужны.

При ошибке восстанавливаются предыдущий образ, его `.env` и снимок базы до миграций. Краткое отключение VPN допустимо. Если сервер выключился в середине операции, следующий запуск сначала восстановит незавершённую транзакцию. При неудаче самой первой установки контейнеры останавливаются, а частичная настройка сохраняется для повторного запуска.

Состояние на VPS:

```text
/opt/network-stack/
  current.json                 # Активный релиз
  last-deployment.json         # Данные для ручного отката
  transaction.json             # Только пока идёт незавершённая операция
  releases/<sha-run-attempt>/  # Код и приватный .env конкретной версии
  state/xui/                   # SQLite и bootstrap-complete.json
  state/caddy-data/             # Сертификаты и ACME account
  state/caddy-config/
  backups/<sha-run-attempt>/xui/
```

Для ручного отката последнего успешного обновления выполните от root на VPS:

```bash
release=$(python3 -c 'import json; print(json.load(open("/opt/network-stack/current.json"))["release"])')
python3 "/opt/network-stack/releases/$release/scripts/deploy.py" rollback
```

Откат возвращает базу к моменту перед обновлением, включая пользователей и пароли того момента. Копии и старые релизы не удаляются автоматически: контролируйте место, сохраняйте текущий и предыдущий релизы и соответствующий снимок. Старые копии могут содержать уже отозванные ключи.

Диагностика операции доступна root через `journalctl -u 'network-stack-deploy-*' --since today`. Подробный вывод CLI и API в Actions намеренно подавлен, поскольку ошибки upstream могут содержать конфигурацию и секреты. Конфиги, ключи и ссылки никогда не загружаются в artifacts.

## Резервная копия вне VPS

Локальный снимок помогает при неудачном обновлении, но не при потере диска VPS. Перед переносом или удалением сервера остановите 3x-ui и Caddy через Compose активного релиза, скопируйте весь `/opt/network-stack` в защищённое хранилище и снова запустите сервисы. Не копируйте работающий SQLite простым `cp`.

Команды от root на VPS создают приватный архив в `/root`, исключают одновременный деплой и возобновляют сервисы даже при ошибке архивирования:

```bash
(
  set -euo pipefail
  umask 077
  flock -n 9 || { echo 'Другая операция уже выполняется'; exit 1; }
  release=$(python3 -c 'import json; print(json.load(open("/opt/network-stack/current.json"))["release"])')
  cd "/opt/network-stack/releases/$release"
  export STACK_STATE_DIR=/opt/network-stack/state
  export STACK_RUNTIME_DIR="$PWD/.runtime"
  trap 'docker compose --env-file .env up -d xui caddy' EXIT
  docker compose --env-file .env stop caddy xui
  tar -czf "/root/network-stack-$(date -u +%Y%m%dT%H%M%SZ).tar.gz" -C /opt network-stack
) 9>/opt/network-stack/deploy.lock
```

Скачайте полученный архив в защищённое хранилище вне VPS. Для восстановления на чистом Ubuntu 24.04/26.04 сначала установите Docker с Compose, загрузите архив в `/root`, проверьте актуальный IP в `.env` и выполните от root (подставьте имя архива):

```bash
tar -xzf /root/network-stack-YYYYMMDDTHHMMSSZ.tar.gz -C /opt
release=$(python3 -c 'import json; print(json.load(open("/opt/network-stack/current.json"))["release"])')
cd "/opt/network-stack/releases/$release"
export STACK_STATE_DIR=/opt/network-stack/state
export STACK_RUNTIME_DIR="$PWD/.runtime"
docker compose --env-file .env up -d
```

Проверьте HTTPS-панель, VPN и Telegram. Сохраняйте `bootstrap-complete.json`: его удаление не является способом ротации ключей. Резервная копия содержит VPN-секреты, хеш пароля и TLS-ключи; архивирование от root сохраняет права файлов и UID mtg.

## Проверки разработки

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
sudo python3 tests/integration.py
```

Интеграционный сценарий использует отдельный Docker-проект, случайные loopback-порты, временные ключи, базу и CA. Он проверяет обе попытки bootstrap, HTTPS с доверенной тестовой CA, настоящий HTTPS-запрос через VLESS, отказ с неверным UUID, смену пароля, включение 2FA и сохранение удаления клиента после пересоздания контейнеров. Созданные контейнеры удаляются. Нужны Compose 2.24.4+ для тестовых `!override`, доступ к реестрам, NTP, Telegram и HTTPS-сайтам.

Проверка с внутренней CA подтверждает HTTPS по IP, включая клиентов без SNI, но не выпуск Let's Encrypt для вашего VPS. Установка на чистый VPS, публичная доступность портов, реальное продление ACME и подключение приложения Telegram проверяются при приёмке на целевом сервере.

Первичные источники: [3x-ui](https://github.com/MHSanaei/3x-ui), [mtg](https://github.com/9seconds/mtg), [Caddy ACME](https://caddyserver.com/docs/automatic-https), [Docker Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
